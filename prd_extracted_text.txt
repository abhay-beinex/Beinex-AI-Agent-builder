Beinex AI Agent Workflow Builder
1. Project Overview
1.1 Background
The UAE government plans to move 50% of public-sector services and operations to autonomous (agentic) AI models within a two-year transformation window. Government entities, and the enterprises that serve them, will need a safe and controlled way to create AI agents and connect them to real business processes.
1.2 What We Are Building
In simple words: a website where a person describes a task in plain language, or drags blocks onto a canvas. The platform turns that into an AI agent or an automated workflow that runs by itself, asks a human to approve important steps, and records everything it did.
The platform has two main features that work together:
Feature
What it does
Result
Agent Builder
The user describes an AI worker in plain language and the platform creates it (name, role, tools, model, rules).
A reusable AI agent that can chat, join workflows, join councils and be shared with other systems
Workflow Builder
The user describes a process in plain language, or drags bricks onto a canvas, to connect triggers, agents, tools, people and logic.
An automated workflow that runs by itself and asks people to approve key steps
In short: agents are the workers, and workflows are the processes that put the workers to use. Any agent built in the Agent Builder can be dropped into a workflow, and a workflow can also be used by an agent as a single tool.

4. Feature 1: Agent Builder (Create Agents from Prompts)
The Agent Builder is a feature in its own right. It lets anyone create an AI agent simply by describing the job in plain language, with no coding. The agent can then be used on its own in chat, or as a ready-made worker inside workflows and councils.
In simple words: an agent is like a new colleague with one clear job. You describe the role, the platform sets the colleague up, you test them, and once approved they can start work.
4.1 What Is an Agent?
Part of the agent
What it holds
Name and avatar
How the agent appears in chat, in the sidebar and on the workflow canvas
Role description
The plain-language instructions (the prompt) that say what the agent does and does not do
Tools
Systems the agent may use (Outlook, SharePoint, web search, databases, any connected API)
Model
The AI brain used, for example noah-verify for checking or noah-decide for recommendations
Knowledge
Document libraries the agent can search (RAG), with citations back to the source
Memory (optional)
What the agent remembers between conversations, with a viewer and a delete button

Owner and approver
The named person responsible for the agent and for approving it
Autonomy level and status
How much freedom it has (Section 6.3) and its state: Draft, Awaiting approval, Live or Paused
4.2 How an Agent Is Built by Prompt
Step
What happens
1. Describe
The user types or speaks (English or Arabic) what the agent should do. Example: “Check supplier invoices against purchase orders and flag any quantity or price mismatch.”
2. Draft agent card
The platform creates the agent: a name, role description, suggested tools, a suggested model and starting rules. If something is unclear (for example, who approves?) it asks a short question first.
3. Review and edit
The user changes anything, either by chatting (“only look at invoices above AED 5,000”) or by editing the card directly. The prompt method and the manual form always show the same agent.
4. Test in chat
The user talks to the draft agent using sample data and checks the answers. Nothing real is touched.
5. Approve and go Live
The owner approves the agent. Status moves from Draft, to Awaiting approval, to Live.
6. Use
The live agent can be chatted with, placed in a workflow, added to a council, or shared with outside systems.

5. Feature 2: Workflow Builder (End-to-End Platform Workflow)
This section shows the journey of a workflow, from an idea in someone’s head to a live, automated process, and then what happens each time it runs.
5.1 The Platform Lifecycle
Stage
What happens
1. Build
The user first creates any agents needed in the Agent Builder (Section 4), then describes the process in words (the platform draws the workflow) or drags bricks and agents onto the canvas. Both methods edit the same underlying definition, so the user can switch at any time.
2. Configure
For each step the user sets the Description, Tools and Model. The platform may suggest the best-fit model (for example noah-verify for checking tasks).
3. Test
“Try with sample data” runs the workflow, or a single step, in a safe mode that does not touch real systems.
4. Approve
The workflow is sent to its owner or approver. It cannot go Live without this approval.
5. Go Live
The workflow is published and switched on. Its triggers are now active.
6. Run
Triggers start the workflow automatically (see Section 6). Agents work, people approve, connectors act.
7. Monitor
Run history, step-by-step traces, dashboards, cost and alerts show what happened and why. Everything is written to the audit log.
8. Improve
Changes create a new version. The previous version can be restored at any time.
5.2 What Happens When a Workflow Runs
The example below follows an invoice through a live workflow. Orange boxes are the points where a person is involved.
Trigger: a new invoice arrives by email (Outlook connector).
Verify agent: noah-verify extracts the invoice data and checks it against the purchase order and contract.
Logic: is the amount above AED 50,000? If not, the workflow continues under the administrator’s limits.
Council: the Procurement council debates; a combined Council View is produced with sources.
Human: an approval card goes to the named approver, who chooses Approve, Reject or Approve with conditions.
Decide agent: noah-decide recommends the posting route and flags risks.
Action: the finance step writes to the system (only after the human step) and drafts the confirmation email.
Notify and audit: the requester is told in chat and every step is stored in the audit log.
In simple words: the same workflow can be created by typing one paragraph, or by dragging eight bricks.
6. Workflow Automation in the Platform
Automation is the main purpose of the platform. Once a workflow is Live, nobody needs to press Start. It runs by itself when its trigger fires, and people are involved only where judgment or authority is needed.
6.1 What the Platform Automates
Area
How it is automated
Starting work
Triggers start workflows on a schedule, on an event, or on a chat command.
Doing the work
Agents read documents, search data, check rules and draft outputs using their tools and models.
Routing
Logic steps send each case down the right path (for example by amount, risk or confidence).
Waiting
The workflow pauses safely for a human decision or a timer and resumes automatically when the answer arrives.
Escalating
Overdue approvals trigger reminders and move to a backup approver.
Recovering
Failed steps are retried; if a model or system is unavailable the workflow switches to a fallback or pauses and alerts.
Recording
Every run, decision and approval is logged without anyone doing anything.
Building itself
A described process is turned into a draft workflow automatically (Section 7.1).
Improving
The platform highlights slow steps, frequent failures and costly models, and suggests changes.

6.3 The Autonomy Dial: How Much Freedom Does a Workflow Have?
Because government clients need control, every workflow has an autonomy level that an administrator or owner sets. It can be raised as trust grows.
Level
What the workflow may do
Typical use
Level 1: Suggest
Prepares drafts and recommendations only. A person performs every action.
New workflows, sensitive services
Level 2: Act after approval
Performs actions only after a person approves (the default).
Payments, official letters, record changes
Level 3: Act within limits
Acts alone for low-risk cases inside set limits (amount, confidence, data type) and asks a person otherwise.
Routine, high-volume, low-value tasks
6.4 Automation Requirements
Triggers: schedule, email, file, webhook/API, chat command and workflow-to-workflow triggers can all start a workflow.
Pause and resume: a workflow waiting for a person or a timer keeps its state, even across restarts, and resumes by itself.
Automatic retries and error paths: each step can retry, and the builder can define what happens if it still fails.
Human gates by rule: thresholds, low confidence or sensitive data automatically bring in a person.
Autonomy levels (Section 6.3) set per workflow and enforced by the platform.
Controls: pause, resume or stop any workflow instantly (kill switch); limits on cost, rate and number of simultaneous runs.
Automatic logging of every run and decision.
Reminders, deadlines and escalation for approvals, with delegation during leave.
Fallback models and systems when the first choice fails or is over budget.
Run queue and scaling so busy periods do not slow down or lose work.
Alerts to chat, Teams or email for failures, long waits and budget overruns.
Improvement suggestions based on run history.
Maintenance windows and blackout calendars when workflows must not run.
Event replay to re-process missed events after an outage.
7. Functional Requirements by Module
7.1 Building a Workflow by Prompt (“Describe it”)
In simple words: the user types, “Every month, check all invoices over AED 50,000 against their contracts, ask the Procurement team to review problems, and let Fatima decide what to escalate.” The platform draws the workflow.
Describe in plain language: type or speak (English or Arabic) a process; the platform generates a draft workflow on the canvas.
Preview and explanation: the draft is shown with each step explained in plain language before anything is saved or run.
Clarifying questions: the platform asks when something is unclear (for example, “Who should approve?”).
Refine by chatting: “Add a step to notify finance” or “Remove the second check” updates the canvas.
Permission-aware: the draft uses only tools, connectors and models the user is allowed to use.
Safe by default: a human approval is inserted automatically before any step that writes to an external system.
Suggestions: the platform proposes improvements, such as running two steps in parallel.
Missing agents: if the described process needs an agent that does not exist yet, the platform offers to create it with the Agent Builder.
7.2 Building a Workflow by Drag-and-Drop (“Build it”)
The same workflow can be built visually. Both methods edit one underlying definition, so users can switch between them freely.
Brick palette: Triggers, Agents (every Live agent from the Agent Builder), Tools, Logic, Human, Council and Workflow bricks can be dragged onto the canvas.
Smart snapping: Bricks can connect only in the correct places. A trigger must come first, and the system cannot make any changes until a person approves or takes action. If a connection is not allowed, the platform explains why.
Visual branching: lines connect nodes and forks such as approve/reject are shown, as in Cohere North’s “User review” step.
Click to configure: selecting a node opens its settings panel (Section 3.1).
Canvas basics: pan, zoom, undo/redo, copy/paste and auto-arrange.
One definition: changes made by prompt or by dragging appear immediately in the other view.
Side-panel chat: “Say what you want on the right” so prompting and dragging work together.
Touch support: large targets and pinch-zoom for showcase displays.
7.3 Workflow Structure and Logic
Triggers: schedule, new email, new file, API/webhook, chat command, event from another system, another workflow.
Logic: if/else, switch, loops, parallel branches, wait/timer, retry on error and an error-handling path.
Defined data flow: each node declares its inputs and outputs, and the user can see “what goes in, what comes out” next to the settings (as in n8n).
Autonomous or reactive: a workflow can run in the background on events, or only when someone asks in chat.
Sub-workflows: any workflow can be used as a single step in another.
Code node: optional JavaScript or Python step for engineers.
7.4 Configuring Each Step (Description, Tools, Model)
Description: a plain-language instruction field with example templates.
Tools picker: shows only the tools the user is authorized to use, grouped as Files, Email, Web, Databases and Custom.
Model picker: lists noah-verify, noah-decide and any other approved model, each with a one-line description and a “recommended for” label.
Advanced tab: output format (text, table, JSON), temperature, maximum length, timeout, retries, cost budget and fallback model.
Test this step: run one node with sample or mock data without running the whole workflow.
Model recommendation: the platform suggests the best-fit model from the description; the user can override.
Last input and output are shown on each node for easy debugging.
7.5 Managing Agents
In simple words: agents are created in the Agent Builder (Section 4). This module covers how live agents are managed and used day to day.
Lifecycle: Draft, Awaiting approval, Live, Paused, with who approved and when.
Owner and scope: each agent has a named human approver and a clear scope (for example, “runs only when asked in chat”).
Instant pause: administrators can pause any agent with a reason attached.
One-to-one chat with rich cards (tables, comparisons, approve buttons).
Knowledge libraries (RAG): document sets an agent can search, with citations back to the source.
Memory: an agent can keep context between runs, with a viewer and a delete button.
Skills library: reusable capabilities (such as “Extract invoice data”) shared by many agents.
7.6 AI Models, Including noah-verify and noah-decide
In simple words: different jobs suit different brains. A model registry lists every available model, and each step simply picks the right one.
Working assumption to confirm with the model team: noah-verify checks and validates (documents, data, claims, compliance) and noah-decide recommends or decides (scoring, routing, approve/escalate suggestions).
Model registry: lists the Noah models plus any approved third-party or client model, with purpose, languages, limits, cost, hosting location, status and version.
Noah models everywhere: available on every agent node and settable as the platform default.
Mixed models in one workflow: for example noah-verify to check, a general model to summarize and noah-decide to recommend.
Confidence and reasoning: every output shows a confidence score and a short reasoning summary where the model supports it; low confidence automatically routes to a human.
Version pinning: a live workflow keeps its tested model version until an administrator upgrades it.
Private hosting: models can run inside the client’s own environment.
Dedicated Noah nodes: a *Verify* node (input: data plus rules; output: pass/fail plus evidence) and a *Decide* node (input: case facts plus policy; output: recommendation, confidence and reasons).
Fallback: if a model is unavailable or over budget, switch to a backup or pause and alert.
7.7 Tools and Connectors
Outlook: triggers (new email, calendar events) and actions (search inbox, draft reply, extract attachments, send email gated by approval).
Web search: live retrieval, allow-lists of trusted sites (such as government registries and sanctions lists) and automatic citations.
Documents: read PDF, Word and Excel and extract tables and fields into structured data.
Data: query databases and data platforms; read and write spreadsheets.
HTTP/API tool: call any web service when no ready connector exists.
Custom tool builder: an engineer registers a new tool with an OpenAPI description or MCP server link.
Credential vault: secrets are stored encrypted; builders never see raw passwords or keys.
Collaboration: Microsoft Teams, SharePoint and WhatsApp for messages and approvals.
Catalogue growth: 100+ connectors over time, prioritized by client demand.
7.8 Human Approvals and Guardrails
Approval step: pauses the workflow and sends an approval card to the named person (in the platform, Teams or email).
Decision-ready card: shows what is proposed, why, the evidence and sources and the model’s confidence, with buttons Approve, Reject, Approve with conditions and Ask a question.
Rules for when a person is needed: amount thresholds, low confidence, sensitive data, or always.
Guardrails: block or flag restricted topics, personal-data leaks and off-policy actions, defined centrally by administrators.
Structured outputs: AI steps must return data in a defined format so later steps do not break.
Spend governance: token and cost budgets and rate limits per user, agent, workflow and department, with alerts at 80%.
Kill switch: administrators can stop all runs of a workflow or agent immediately.
Deadlines, reminders, escalation and delegation for approvals.
7.9 Councils (Multi-Agent Deliberation)
In simple words: for difficult cases, several specialist agents discuss like a committee. Each cites its sources, they challenge each other, and a combined recommendation goes to a human.
Create a council by choosing agents and a goal (for example, a Procurement council made of Contract Review, Policy Q&A and Invoice Checker).
Council View: agents speak in turn, cite their sources and produce one combined view.
Advisory only: any action that changes data needs a human decision click.
Two-way link with workflows: a workflow can call a council as a step, and a council can start a workflow.
Cross-examination: one agent can challenge another’s finding (for example, “this contract has expired”).
Supervisor and worker pattern: a lead agent splits work among specialists.
7.10 Interoperability: Working with Client Platforms (e.g. Copilot Studio)
In simple words: clients should not have to throw away what they already own. Their agents can use ours, and ours can use theirs.
MCP (Model Context Protocol) is an open standard that lets AI agents use tools and data from other systems in a uniform way. A2A (Agent-to-Agent) is an open standard for agents from different vendors to hand work to each other. OpenAPI is a standard description of a web service so other software can call it.
Outbound (Beinex as provider): every agent, council and workflow can be exposed as an MCP server and as an OpenAPI/REST endpoint with a downloadable specification.
Inbound (Beinex as consumer): a client registers an external agent by pasting an OpenAPI specification or MCP link; it appears with an avatar, can be chatted with, added to councils and dragged into workflows.
Copilot Studio: a Beinex agent can be added to Copilot Studio as a tool or connector, and a Copilot Studio agent can be called from a Beinex workflow.
Secure calls both ways: webhooks, API keys and OAuth.
Same governance for external agents: the same approvals, logging and spend limits apply.
A2A gateway: agents from different vendors can hand work to each other.
Import/Export of workflows and agents as files, to move between Development, Test and Production and between clients.

9.2 One Definition, Two Ways to Build
The prompt builder and the drag-and-drop canvas both read and write the same declarative workflow definition (JSON). This is what makes switching between methods possible. Illustrative example:
{
  "name": "Monthly compliance check",
